# CPLM → Traverse Edge — Gap Analysis (completed worksheet)

**Date:** 2026-08-04 · **Repo:** `AMS-OpenBridge` @ `phase8-polish` (22 commits, single contributor)
**Method:** code, compose files and build files only. Documentation was treated as a claim to be checked, never as evidence. Every `YES`/`PARTIAL` carries a `file:line`.

## Conclusion first

**The engine ports almost for free. The data does not exist.**

Traverse runs **Flink 1.18.1 on Java 11** — the exact target ([docker-compose.yml:320](infra/docker/docker-compose.yml#L320), [pom.xml:12-14](src/flink/pom.xml#L12-L14)). RocksDB + incremental checkpoints are already the cluster default. Kafka, IoTDB, PostgreSQL, a real Sparkplug live plane, a working `binding-resolver`, and real RS256 auth are all present and deployed.

Three findings dominate everything else:

1. **This is not a foreign-jar drop-in — it is a fork merge.** `CPA/CPAMAIN/src/flink` and `src/flink` are the *same Maven module* (`com.ams:ams-flink:1.0-SNAPSHOT`, identical Flink/connector versions) diverged from a common ancestor. They share `com.ams.flink.PipelineConfig`, `PipelineOperators`, `RawLoopData`, `LoopKpiResult`, `LoopKpiStreamJob`, and both build to the **same jar filename** that compose bind-mounts. `PipelineConfig`'s constructor has diverged on both sides. The good news: the `com.ams.flink.cplm` package has **zero imports from any other `com.ams` package** — verified — so it lifts cleanly. See §4.
2. **Traverse has no process-sample stream.** `loop-raw-data` exists as a topic name, a POJO ([RawLoopData.java:11-17](src/flink/src/main/java/com/ams/flink/RawLoopData.java#L11-L17)) and a consumer job — and **has zero producers**. The only running numeric feed is `live.metrics`, one scalar per message, fed by a Python sine-wave simulator that is not even in the main compose file. No PV/SP/OP tuple, no mode, no valve position as a loop field. **D4, D5, D6 and D8 are all NO.**
3. **Assets have no non-hierarchical edges.** Definitively. Two tables total in the assets DB, one nullable `parent_id`, no navigation collections, no relate endpoint. **G13 stays `NOT_EVALUATED` until an edge table is built.**

Reuse list: Flink, Kafka, IoTDB, PostgreSQL/Timescale, EMQX + Sparkplug bridge, Redis snapshot cache, `binding-resolver`, auth-service (RS256/JWKS/permissions), the ISA-18.2 alarm state machine, Prometheus/Grafana skeleton.
Build list: the sample producer, `cpm.*` + `analytics.*` schemas, result→store consumers, asset edges, the CPA API module, multi-series historian reads, and the whole frontend.

**Contradictions between Traverse's own docs and its code are listed in §10 — there are six, and one of them is in `CLAUDE.md`.**

### K-B — naming convention

Two taxonomies coexist, unenforced, undocumented in code: dash-case (`raw-alarms`, `loop-raw-data`, `loop-kpis-5m`, `kpi-*`) and dot-case (`live.metrics`, `live.alarms`, `alarm.state.delta`, `flink.state.alarm.delta`, `analysis.executions`) — both listed side by side in [kafka-reset-lab-topics.ps1:13-38](scripts/kafka-reset-lab-topics.ps1#L13-L38). `flink.state.alarm.delta` and `alarm.state.delta` are two orderings of the same words. **No topic carries a version suffix**; versioning is in-payload (`schemaVersion: 1`) and only on alarm-lifecycle messages ([OpcEventStreamJob.java:192,233,255](src/flink/src/main/java/com/ams/flink/OpcEventStreamJob.java#L192)). CPLM's `a.b.c.v1` names are compatible with the dot-case family and strictly better than either.

### D-A — does Traverse's tag model expose valve position as a distinct role? **No.**

There is no role concept on a tag at all. `role` in Traverse means either a *transport* role on a binding **request** (`live|history|alarm|all`, stringly-typed at [PathResolver.cs:35-38](src/services/binding-resolver/Services/PathResolver.cs#L35-L38), no enum file) or an *RBAC* role ([17_traverse_auth_schema.sql:16](database/scripts/17_traverse_auth_schema.sql#L16)). Neither is a signal role. Achieving CONFIRMED-grade diagnosis requires adding a signal-role concept — this is the single highest-value data change in the whole port.

## 8. Questions answered explicitly

**1. Flink version / Java runtime — does the jar drop in?**
The **runtime** drops in: `flink:1.18.1-java11` matches `<flink.version>1.18.1</flink.version>` + Java 11 exactly, with identical connector versions and no Scala coupling. **But you should not ship two jars.** Both modules build `ams-flink-1.0-SNAPSHOT.jar`, and compose bind-mounts that exact path in five places ([docker-compose.yml:363](infra/docker/docker-compose.yml#L363), `:438`, `:1050`, `:1077`). Merge the `com.ams.flink.cplm` package into `src/flink` and rebuild one jar. Two additional cautions: Traverse's shaded jar already leaks ~5 383 `org/apache/flink/**` classes (the connectors don't mark Flink `provided`) with **no relocations and no `ServicesResourceTransformer`** ([pom.xml:110-145](src/flink/pom.xml#L110-L145)) — a second fat jar on the same classloader would be a real hazard. *(A Jackson-flavour mismatch was also flagged here in an earlier draft; performing the merge disproved it — the `cplm` package imports only `org.apache.flink.shaded.jackson2.*`, the same as Traverse's own jobs.)*

**2. Does a process-sample stream exist? Does it carry quality/mode/VP? At what rate?**
**No.** `loop-raw-data` has the right contract and **zero producers**. `live.metrics` runs at **2 s** from a `math.sin` simulator that is not in the main compose; it carries a hardcoded `quality=192`, **no mode**, and valve position only as a separate device+metric message. Nothing anywhere in Traverse produces PV/SP/OP as a tuple.

**3. Does the asset model support relationships? (G13)**
**No.** Parent/child containment only. Verified against DDL, the EF model and the route surface. G13 will report `NOT_EVALUATED` / `NO_UPSTREAM_LINKS` on day one, and an edge table plus API must be built to change that. The richer model in `database/migrations/phase0/` is explicitly disowned and unmounted.

**4. Which historical query capabilities exist? Is decimation server-side?**
Decimation **is** server-side (IoTDB `GROUP BY ([start,end), interval)`). H1 YES (but `last_value`-only, cap 2000), H2 PARTIAL (offset paging, real cap 500 not 10 000), H3 PARTIAL (no first/last), H4 PARTIAL (alarm-prefix default), **H5 NO**, **H6 NO**, **H7 NO**.

**5. What runs in the live plane today, end to end?**
`AlarmIngestionService` HTTP-polls `http://192.168.1.51:8010/api/current-alarms` every 2 s → Kafka `raw-alarms` → Flink `OpcEventStreamJob` (ISA-18.2 state machine) → `current-alarm-state` → Flink `LiveStateJob` (RBE) → `live.alarms` → `sparkplug-edge-node` → Sparkplug B over MQTT/EMQX + Redis snapshot → browser (`mqtt` + `sparkplug-payload`) → zustand → Designer symbols. In parallel, SignalR `AlarmHub` pushes alarm/SOE/ack events to the React client. The **process-value** branch of the same bridge is fed only by the opt-in Python simulator, and the Flink `live.metrics` branch is dead (K6).

**6. Production or shared? Change/deployment process?**
**A single-developer lab stack, not production.** Repo has 22 commits and one contributor; current branch `phase8-polish`. `run-all.ps1:6-8` describes itself as starting "every **lab** service". Evidence throughout: seeded demo plants (houston/dallas, [15_traverse_assets_2site_plant.sql](database/scripts/15_traverse_assets_2site_plant.sql)), a sine-wave simulator, `EMQX_ALLOW_ANONYMOUS: "true"`, IoTDB `root:root` hardcoded and un-overridable ([IoTDbClient.cs:17-19](src/services/historian-bff/IoTDbClient.cs#L17-L19)), default service key `traverse-internal-dev-key`, bootstrap admin `ChangeMe123!`, `ASPNETCORE_ENVIRONMENT: Development`, and floating image tags (`timescale/timescaledb:latest-pg15`, `provectuslabs/kafka-ui:master`, `dpage/pgadmin4:latest`). Deployment = `docker compose up` via `run-all.ps1`; **rollback is `docker compose down` plus a volume wipe**, because schema delivery is initdb-once. There is no staging environment and no CI-gated deploy in the repo. Helm charts exist but are **incomplete** — `infra/helm/ams/values.yaml:38-43` declares 16 TaskManager replicas while `charts/flink/templates/` contains **only** `jobmanager-deployment.yaml`.

**7. Does Traverse bridge OPC-UA/DCS to the bus?**
**No.** `src/services/opc-connector/` contains exactly one file — `.dockerignore` — and is **absent from docker-compose**. `raw-opc-events` does not exist (it is on the reset script's *delete* list, [kafka-reset-lab-topics.ps1:41-44](scripts/kafka-reset-lab-topics.ps1#L41-L44)). The real ingestion is `AlarmIngestionService` HTTP-polling a hardcoded LAN IP ([AlarmIngestionService.cs:20,158](src/backend/AMS.Api/BackgroundServices/AlarmIngestionService.cs#L20)), and it carries **alarms only**. `configuration.opc_servers` / `configuration.opc_connections` are server/connection rows with **no per-item tag table** ([02_alarm_schema.sql:11-33](database/scripts/02_alarm_schema.sql#L11-L33), [03_apply_ef_migrations.sql:131-153](database/scripts/03_apply_ef_migrations.sql#L131-L153)). **CPLM's missing edge adapter is still missing after the port.**

**8. Historian retention/TTL and numeric-type conventions?**
TTL exists but is **misaimed**: 365 d on `root.ams.site1.alarms`, 90 d on `root.ams.site1.metrics` — and **nothing writes to the metrics tree** ([iotdb-init-ttl.sh:44-53](infra/docker/iotdb-init-ttl.sh#L44-L53)). Real process values land under `root.<site>.<unit>.<device>.<measurement>`, which has no storage group and no TTL. Numeric types are **undeclared**: `enable_auto_create_schema: "true"` plus a writer that string-concatenates values into SQL ([AlarmMetricPublisher.java:270-271](src/services/sparkplug-edge-node/src/main/java/com/ams/sparkplug/AlarmMetricPublisher.java#L270-L271)) means the type is inferred per-literal at first insert. Set this correctly during the port: declare `root.<site>` storage groups explicitly, `CREATE TIMESERIES ... DOUBLE` for all numerics, and `SET TTL` on the tree that is actually written.
