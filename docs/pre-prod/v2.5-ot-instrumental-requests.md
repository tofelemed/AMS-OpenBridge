# v2.5 — what we need from the OT gateway team and from Instrumental

**Date:** 2026-09-25 · **From:** Traverse CPA (loop performance) · **Release:** v2.5 on Marun ·
**Please answer by:** before the v2.5 window (dates in the release plan)

Two feeds reach the loop-performance system: the **control-loop signals** from the OT gateway (already live) and, new in
v2.5, **transmitter health** from Instrumental (NE107). This note says, per feed, what stays as it is, what we must have
confirmed, what would make the new release useful, and what is optional. Items are tagged **MUST** (needed for correct
results), **SHOULD** (needed for a v2.5 feature to deliver value), **OPTIONAL** (nice to have).

**Short version for the OT gateway team: nothing has to change in the payload. The system keeps working with exactly what
you publish today.** The requests below are about confirming what you send, keeping the connection alive across your
maintenance, and a few additions that unlock new analyses.

---

## Part B — Transmitter health (Instrumental team)

v2.5 adds a **read-only** subscriber for Instrumental's NE107 device state. Until your publisher exists, every loop reads
"transmitter health: not configured" — that is the intended state, not a fault. The full contract with JSON schemas is
[`docs/next-release/instrumental-health-contract.md`](../next-release/instrumental-health-contract.md) and
`contracts/instrumental-health/v1/*.schema.json`; the field-by-field parse rules are `ingestionv2.5.md` §2 (repo root).
The schema is strict (`additionalProperties: false`): aliases such as `first_seen` or `code` are rejected.

### B.2 How a transmitter is mapped to a loop (what we do with I3 + I4)

1. The **binding** is the mapping: `(loop tag, signal role) → device_id`, effective-dated (`valid_from`, open-ended),
   one primary device per signal at any time (the database refuses overlaps), with `installation_id` and `source_id`.
   A replaced transmitter is a new binding from its install date; history keeps the old one.
2. We create bindings from your device inventory plus the instrument assignment list (which transmitter feeds which loop's
   PV, which positioner feeds VP) through `POST /api/v1/cpm/loops/{loop}/instrument-bindings` — API only in v2.5, scripted
   in bulk. What we need for that is a CSV: `loop_tag, role (PV|VP|SP|OP), device_id, installation_id, source_id, valid_from`.
3. Your device state → per-device intervals → per-loop / per-role **eligibility** (`ELIGIBLE / LIMITED / INELIGIBLE /
   UNKNOWN / NOT_CONFIGURED`) → shown on the loop, in the Historical and Evidence views, and used by the engines:
   a Failure on the PV transmitter excludes the loop's window with the reason "instrument health", never a silent pass.
4. We are read-only toward Instrumental: acknowledging a loop episode never acknowledges a device condition.
