Ships **traverse-ingestion-service, cplm-api, historian-bff, the Flink image + JAR, ams-frontend**.
Additive schema (six scripts merged) applied **online before the image swap**, seven new Kafka
topics created **before the jobs start**, every CPLM job cancelled and resubmitted plus three

**The traps, in order of cost:**

1. **Schema before image.** The new cplm-api consumers write columns and tables that only cpm-07 creates
   (`method_run_ids`, `bundle_hash`, `analysis_run`, `evidence_*`, `response_*`, `gate_config_*`, …). The
   image self-heals only the pre-v2.5 tables. Run cpm-07, then cpm-07b, then cpm-08, and only then load images.
2. **Topics before jobs.** The plant broker has auto-create off. A CPLM job whose sink topic is missing fails
   at its first record; the Response job announces its capability on the ACK topic at start. Create the seven
   topics first (idempotent).
3. **The signing key.** The Flink containers must carry `CPLM_GATE_CONFIG_KEY` (compose sets it from
   `TRAVERSE_SERVICE_KEY`). Without it nothing breaks, but every configuration bundle is NACKed `UNSIGNED`
   and no deployment can ever be verified. Prove it after the recreate (step C5).
4. **Every CPLM job is resubmitted.** The operator chains changed (peer fan-out, control broadcast with a side
   output, response captures): no savepoint restore across this release. Short windows rebuild within the hour;
   12 h / 24 h verdicts need up to a day (as in V3).
5. **cpm-07b runs with cplm-api stopped.** It swaps the unique keys of the three result tables (the old
   consumer's `ON CONFLICT` needs the old key, the new consumer's the new one), so: cpm-07 online, then
   `docker stop traverse-cplm-api`, cpm-07b (plain index builds, seconds at plant size), then the images and
   `deploy.sh` start the new consumer within the same minute. Results queue in Kafka meanwhile. If cpm-07b
   fails half-way, re-run it: every statement is `IF NOT EXISTS` / `IF EXISTS`.

## D. Afterwards, not part of the release

- **Transmitter health** stays `NOT_CONFIGURED` for every loop until Instrumental delivers its NE107
  publisher; then one `INSTRUMENTAL_HEALTH` data source per publisher (contract:
  `docs/next-release/instrumental-health-contract.md`) and device bindings per loop / role
  (`POST /loops/{id}/instrument-bindings`). By design, not a defect.
- **Governed configuration** starts empty: every loop runs the factory layer (= the class packs, exactly
  as before) until a site drafts, validates, approves and activates a bundle in Gate Configuration. The
  first activation of a scope has no previous bundle to roll back to.
- **Retention** of the result tables is still an ops decision (`ops/cpm-05-gate-results-retention-check.sql`);
  evidence chunks expire by record class (STANDARD 90 d, PINNED never) through the sweeper.
- `--evidence-emit` (EPISODES by default) and `--g12-delay-min-s` are job args on the Response / engine jobs
  (`migration/04b-submit-flink-jobs.sh`).

## Rollback

Schema is additive — leave it (the old images ignore the new columns and tables). Reload the previous
images from `/tmp/pre-v2.5-images.txt`, restore the previous JAR, `docker rm -f ams-flink-taskmanager
ams-flink-jobmanager`, `deploy.sh --prod`; the three new jobs fail to submit from the old jar (no entry
class) — expected, cancel nothing else. The seven new topics and the new permissions can stay.

**cplm-api is the one exception.** Its old consumer upserts `ON CONFLICT (loop_id, window_kind, window_end,
source)`, the key cpm-07b replaced. Before starting the OLD cplm-api image, restore that key with cplm-api
stopped:

```sql
-- traverse_cplm, cplm-api STOPPED. Fails if v2.5 wrote a second row for one window under another bundle
-- (a re-evaluation); delete those rows first: DELETE FROM analytics.cplm_gate_results WHERE bundle_hash <> 'legacy' AND purpose <> 'LIVE';
CREATE UNIQUE INDEX IF NOT EXISTS uq_cplm_gate_results_window ON analytics.cplm_gate_results (loop_id, window_kind, window_end, source);
CREATE UNIQUE INDEX IF NOT EXISTS uq_cplm_short_window ON analytics.cplm_short_feature_results (loop_id, window_kind, window_end, source);
CREATE UNIQUE INDEX IF NOT EXISTS uq_cplm_long_window ON analytics.cplm_long_feature_results (loop_id, window_kind, window_end, source);
```

The simpler rollback is to keep the v2.5 cplm-api (it reads and writes pre-v2.5 rows as `legacy`) and roll
back only the jar / ingestion / frontend / historian-bff.
