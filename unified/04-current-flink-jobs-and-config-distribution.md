### 2.2 Configuration acquisition per job

**Alarm jobs (1-6): CLI args + env, everything else compiled in.** `PipelineConfig.fromArgs` (`PipelineConfig.java:61-104`) parses `--bootstrap.servers`, `--raw-alarms.starting-offsets`, per-operator `--parallelism.*`, `--iotdb.*`; env `KAFKA_BROKERS`, `DB_URL/DB_USER/DB_PASS` (:82-84), `IOTDB_*` (:98-101). `DB_URL` is read but **no job uses JDBC** (`OpcEventStreamJob.java:22` "no Flink JDBC sinks"; `flink-connector-jdbc` in `pom.xml:47-50` is an unused dependency). Behaviour constants are hardcoded: severity→priority bands (`PipelineOperators.java:174-178`, :528-536), flood band ≥950 (:399), the CRUSHER/CONVEYOR/FEEDER/MOTOR root-cause taxonomy (:312-318), fallback server GUIDs (:44-45), IoTDB prefix `root.ams.site1.alarms.` (`IoTDBPersistenceJob.java:36`), KPI flood thresholds 50/20/10 (`AlarmKpiStreamJob.java:125-133`), 7-day state TTLs. No DB polling, no HTTP, no config topic, no broadcast state in any alarm job.

**Analysis job (6): configuration rides in the data message.** Each `traverse.analysis.executions` command carries `expression` and `inputs{}`; the job evaluates arithmetic only (`AnalysisExecutionJob.java:259-298`, `ExpressionEvaluator`), no per-entity state.

**CPLM jobs (7-12): CLI args + env + ONE Kafka control broadcast with checkpointed broadcast state.**
- Args/env: `CplmJobConfig.fromArgs` (`CplmJobConfig.java:57-82`) - topics, group, window hours, out-of-orderness; `CPLM_GATE_CONFIG_KEY` / `TRAVERSE_SERVICE_KEY` (HMAC key, :85-89), `CPLM_SITE` / `TRAVERSE_SITE` (:91-95); `SPINE_CONSUME_CANONICAL`, `IIMP_CANONICAL_PARAM_TOPIC`, `IIMP_META_TOPIC` (`CplmParameterSetBroadcastSupport.java:59-74`); `--evidence-emit all|episodes|none` (`evidence/EvidencePolicy.java:19-39`); G12 settings `--g12-*` (`response/ResponseJobConfig.java:230-254`).
- Control broadcast: `buildParameterUpdateStream` (`CplmParameterSetBroadcastSupport.java:113-131`) unions the compacted **registry metadata topic** `traverse.cpa.ams.metadata.updates` (earliest, group `<base>-profile-broadcast-legacy`) and the compacted **gate-config bundle topic** `traverse.cpa.context.gate-config.v1` (group `<base>-gate-config-broadcast`), optionally `context.parameter-set.v1`. It is `.broadcast(PROFILE_STATE)` with `MapStateDescriptor<String,String>` (:46-50) into a `BroadcastProcessFunction` (:166) that is `CheckpointedFunction`; the Javadoc states "no static map - a restore reproduces exactly the attributes and bundles in force" (:34-41). The control stream is marked idle after 1 s so it never holds the sample watermark (:133-143).
- What the metadata records carry (`CplmMetadataEnvelope.java:9-16`, :36-74): attribute keys `<assetUuid|loopId>:cplm.loop.engineering`, `cplm.loop.model`, `cplm.loop.evidence` (peers/step tests), `cplm.loop.binding`, `cplm.dynamics.override`, `cplm.dynamics.class.<CLASS>` (`CplmDynamicsParameterSetSupport.java:24-32`), and `{__tombstone:true,key}` which removes a key and its prefix (:38-42). Producer: cplm-api `CpmLoopRegistryService.cs:361,445` (topic default `traverse.cpa.ams.metadata.updates`, key = loop_id).
- What the bundle records carry (`config/GateConfigBundle.java:143-166`): `record_kind: GATE_CONFIG_BUNDLE`, `phase PREPARE|APPLY`, `deployment_id`, `bundle_id`, `hash` (SHA-256 of canonical `{layers,resolved}`), `scope {site,kind SITE|PROFILE|LOOP|REGIME}`, `change_class POLICY|STATE_BOUNDARY|DEPLOYMENT`, `effective_from_ms`, `layers[]`, `resolved.properties{}` + `resolved.execution_plan`, `signature` (HMAC-SHA256, produced by cplm-api `BundleEnvelope.cs:39-49`, keyed by `bundle_id`).
- Handshake (`config/BundleBroadcastHandler.java:41-115`): PREPARE → verify signature (`UNSIGNED`), validate against the jar's 165-property catalogue (`config/PropertyCatalogue.java:26-33`, resource `/cplm/gate-config/property-catalogue.json`), store under `gate-config:prepared:<hash>` → ACK/NACK naming every reason; APPLY needs a prior PREPARE (`NOT_PREPARED`), `STATE_BOUNDARY` increments `gate-config:epoch`, the bundle joins the scope's active list (last 4). ACK/NACK records leave through a side output to `traverse.cpa.context.gate-config.acks.v1` keyed `bundle_id` (`CplmParameterSetBroadcastSupport.java:52-53,:108-111`; `config/ConfigAck.java:34-58` carries job, subtask, jar sha, commit, topology generation). Every CPLM job announces a `CAPABILITY` record at start (`config/CapabilityRecord.java:345-390`) from an unbounded `AnnounceOnceSource` (:464-496). cplm-api's `CplmConfigAckConsumerService.cs:13-48` (one member) drives the deployment state machine to `ACTIVE_VERIFIED` (`changes_tracker.md:1945`).
- Resolution per record: `resolve()` (`CplmParameterSetBroadcastSupport.java:257-276`) = class pack YAML (`resources/cplm/loop-dynamics-profiles.yaml:1-40`, classpath) → registry attributes (override → class → engineering/model) → effective bundle LOOP > PROFILE > SITE by `effective_from_ms ≤ decision time` (`config/EffectiveBundleSelector.java:44-75`), overlaid through `BundleProfileMapper` (:82-110). The resolved profile is **stamped onto each sample / long record** (`CplmNormalizedSample.java:39`; :297, :311) so windows depend on nothing JVM-local. A window decides at its end time, so no result mixes two bundles; `STATE_BOUNDARY` epochs mark windows straddling the boundary `WAITING/WARMUP` (`identity/ResultIdentity.java:29-33,:84-88`).
- The Instrument Context job has its own broadcast (`CONTROL_STATE`: loop bindings from the metadata topic + source availability, `CplmInstrumentContextJob.java:165-183`) and is the **only `KeyedBroadcastProcessFunction`** in the fleet; on a binding or OFFLINE record it walks keyed state with `applyToKeyedState` and re-emits contexts (:273-283,:293-305).
- Bounded jobs (replay/reconstruction) rebuild the same lookup with a plain `KafkaConsumer` reading both compacted topics to end offset (`CplmParameterUpdateReader.java:391-426`).
- **Not** configured through the broadcast: `LoopLiveRbeJob` (single global deadband arg, :97; audit L7), the Short job's window set (compiled, mirrored by cplm-api `/resolutions`, `CplmShortFeatureStreamJob.java:40-42`), and anything the `ExecutionPlanCapacity` declares `FIXED_COMPILED` (`changes_tracker.md:1947`).

**Flink CEP:** absent. `pom.xml` has no `flink-cep` artifact; no `org.apache.flink.cep` import exists (grep of `src/flink`). "CEP"/"correlation-engine" in the alarm job are pass-through maps plus string matching (`PipelineOperators.java:292-347`; `PipelineConfig.java:77-79` keeps `parallelism.cep` only as an alias).

### 2.3 Asset identity in streams

- **Alarms:** key = `serverId|source|condition|subCondition` (`AlarmKeys.java:228-230`); `alarmId` = the feed's explicit id, else an MD5-derived UUID of that key, which "must match AMS.Api StableGuid" (:224,:232-244; `PipelineOperators.java:56-59`). `EnrichmentMap` derives only priority/category/`opcAttributes` (:161-205) - **no asset-model lookup, no UNS path** in Flink. The alarm→IoTDB path is `[^A-Za-z0-9_]→_` over `alarmId` and is "THE canonical alarm-identity rule" shared with binding-resolver `/resolve/alarm` and the browser (`IoTDBPersistenceJob.java:127-134`); punctuation-only collisions are logged, not prevented (:80-102).
- **Loops:** key = `loop_id` (tag such as `FIC10409`); `asset_uuid` and `site` are optional tuple fields (`CplmNormalizedSample.java:15-33`) written by ingestion-service `LoopJoiner.cs:32-55` (schema 1.1 adds `roles{}`, `binding_revision`, `grid_seconds`; `contract/TupleCodec.java:26-40` synthesises roles for 1.0). Profile lookups try `assetUuid:` then `loopId:` prefixes (`CplmDynamicsParameterSetSupport.java:86-96`). Peers are a flat list per loop from `cplm.loop.evidence` (`CplmPeerFanoutSupport.java:19-27`).
- **Devices:** health records keyed `tenant|site|device`; bindings map loop signal roles to devices as of a time (`health/LoopHealthContext.java:18-39`, key `context_key = loop:<loop>:<role>` / `device:…`).
- **Entity id for a living-asset runtime:** nothing keyed by UNS path or asset hierarchy exists in Flink. **(inferred)** an `entity_id` would have to come from asset-model via ingestion (the loop tuple already carries `asset_uuid`) and, for alarms, via a new enrichment step or binding-resolver's alarm→asset resolution.

### 2.4 LiveStateJob

Consumes the compacted `traverse.alarm.current-alarm-state`; for each `alarmId` it merges partial `ACK_STATE_UPDATE` / `ALARM_STATE_DELETE` records onto the last full upsert (`LiveStateJob.java:156-165,:319-331`), derives `state` from `conditionActive`/`acknowledged` (:177-182), and emits only when the fingerprint `state|severity|ack|active|priority` changes (:184-187) with `rbeTs = wall clock` (:200). It writes **Kafka only**: `traverse.alarm.live.alarms` and `traverse.alarm.live.alarm.metrics`, both keyed `alarmId` (:87,:108). Redis and MQTT are written by **sparkplug-edge-node** (`AlarmMetricPublisher.java:31-42`): device = sanitised `sourceName` (:258-261), MQTT `spBv1.0/<group>/DDATA/<edge>/<device>` (:456,:568), Redis `snapshot:metric:<group>:<edge>:<device>:<metric>` = `{v,q,ts}` via `SETEX` with `REDIS_TTL_SECS` (3600 s default, `SparkplugConfig.java:87`; :515-523) plus `snapshot:devices` / `snapshot:index:<device>` sets. **Quality is not computed** by LiveStateJob; the ACK stub hardcodes `quality: 192` (`OpcEventStreamJob.java:308`) and the edge node defaults alarm quality to 192 (:302). **Staleness is not computed** for alarms; the loop branch carries `sourceTs/verifiedTs/emissionTs` (:359-365) and `LoopLiveRbeJob` republishes a 300 s heartbeat whose only advancing field is `emissionTs` (`LoopLiveRbeJob.java:62-88`) - consumers must read the timestamp to see age.

### 2.5 IoTDBPersistenceJob

`raw-alarms` → `parseToRow` (`IoTDBPersistenceJob.java:111-180`): device path `root.ams.site1.alarms.<sanitised alarmId>` (:36,:132-134), timestamp = `eventTimeEpochMs`/`activeTimeEpochMs` else now (:137-138), 7 measurements `severity,state,ack_status,condition_active,priority,source_name,condition_name` (`IoTDBAlarmRow.java:216-217`). `FailLoudIoTDBSink` buffers `iotdb.batch-size` rows (default 500, `PipelineConfig.java:102`), flushes at batch size and inside `snapshotState`, 3 attempts / 2 s backoff, and **throws** so a failed write fails the checkpoint (`FailLoudIoTDBSink.java:15-38,:44-45`). Loop samples go to IoTDB from ams-api `RawLoopIotDbConsumer` (group `traverse-cpa-iotdb-raw-loop`, `RawLoopIotDbConsumer.cs:72-81`), not from Flink.

### 2.6 CPLM jobs

- Loop config, param roles and engineering ranges reach the jobs on `traverse.cpa.ams.metadata.updates` (§2.2); roles themselves are resolved upstream by ingestion-service and arrive in the tuple's `roles{}`.
- Gate thresholds: class pack → registry override → governed bundle (§2.2). Windows are compiled (`CplmShortFeatureStreamJob.java:26-42`; long cadence `CplmLongDiagnosticsStreamJob.java:51-59`); `--window-hours` is accepted but the long job ignores it (audit L8).
- Results: JSON to `clpm.feature.short.v1` / `feature.long.v1` / `gate.results.v1` / `condition.v1` / `response.results.v1` / `gate.evidence.v1`, all keyed `loop_id` or `method_run_id` through `KafkaSinks.keyedByJsonField` (`CplmKafkaSink.java:291-297`). Every result stamps `bundle_hash`, `context_revision` (= bundle epoch), `jarSha256`, `sourceCommit`, `contractVersion`, `dataset_hash`, `method_run_ids`, `evaluation_state` (`CplmGateResult.java:40-58`; `identity/ResultIdentity.java:26-73`).
- Consumer-group traps: the persisting consumers `traverse-cpa-cplm-results` / `…-frames` must have exactly one member or partitions split silently (`docs/cplm-consumer-cutover-runbook.md:7-12`); the Flink `KafkaSource` does not use group coordination, so a duplicate job double-consumes every partition (`flink-job-supervisor.sh:69-79`); the compiled default input topic was once dead, so submitters must pass `--input-topic` (`flink-submit-cplm.sh:23-26`); fusion's condition source starts `LATEST`, so submit it last (:5-7).
- Plant retention (`migration/kafka/topics.txt`): samples 12 h, `feature.short` 2 h, `feature.long` 6 h, evidence 1 h, `gate.results` 3 d, compacted `gate-config` / `metadata.updates` / `parameter-set` / `instrument-health` context never time-limited.

### 2.7 KPI jobs

`AlarmKpiStreamJob` is the only ISA-18.2 KPI job: alarm rate on a global `windowAll` sliding 10 m / 1 m with flood bands 50/20/10 compiled in (:77,:111-136) and a standing count on one `GLOBAL` key (:94-98,:139-172; `oldestStandingDurationMs` hardcoded 0). `AlarmKpiResult.java:214-226` also defines `BAD_ACTOR` / `HEALTH_SCORE` shapes with no producing branch. The state-machine job's `KpiMap` produces JSON that reaches no sink (`OpcEventStreamJob.java:131-136`). KPI definitions live in code, not configuration; ams-api's `AnalyticsController` re-derives KPIs from SQL (audit C7).

### 2.8 Serialization

JSON strings everywhere: `SimpleStringSchema` sources/sinks, records built by hand with shaded Jackson `ObjectNode`. No Avro, Protobuf or schema registry. Versioning is a field: `schemaVersion: 1` on alarm outputs (`OpcEventStreamJob.java:227,:268,:289`; `AlarmKpiResult.java:209`) and CPLM results (`CplmGateResult.java:40`) with `contractVersion "v1"` (`identity/BuildIdentity.java:32`); the samples tuple carries `schema_version 1.0|1.1` with a 1.0 fallback (`TupleCodec.java:9-14,:31-40`). Evolution is additive with dual-name readers (`AlarmJson.text(node,"a","b")`) and comments record incompatible shapes on one topic (audit A9). Flink state uses POJO/`TypeInformation.of(class)` (`CplmLongDiagnosticsStreamJob.java:156-163`) - **(inferred)** any change to those Java types breaks checkpoint restore; CHG-028 shipped as "cancel and resubmit, no savepoint restore across this release" (`changes_tracker.md:1959`).

## 4. Constraints, settled decisions and traps

1. **Flink-only compute** (`MIGRATION_LOG.md:294`; `architecture_document.md:112`): no service recomputes a KPI or gate; cplm-api stores Flink JSON verbatim. The .NET `AlarmStreamProcessorService` is not registered (`docs/flink-only-orchestration.md:3`).
2. **PostgreSQL is written only by the API projection consumers**, never by Flink (`OpcEventStreamJob.java:22`); Flink writes Kafka and IoTDB only. Redis and MQTT are reached through sparkplug-edge-node.
3. **Compacted topics need keyed records** or the broker rejects them and the connector can swallow it; all sinks go through `KafkaSinks.java` (:127-138). Compacted today: `current-alarm-state`, `kpi-standing-snapshots`, `context.gate-config.v1`, `ams.metadata.updates`, `context.parameter-set.v1`, `context.instrument-health.v1`.
4. **One member per persisting consumer group** (`docs/cplm-consumer-cutover-runbook.md:7-12`) and never two copies of a Flink job (`flink-job-supervisor.sh:69-79`).
5. **Deploying a jar = cancel and resubmit** (a restart deploys nothing; ZK-HA restores old blobs; stop the supervisor first) - `changes_tracker.md` CHG-008 §1, `docs/next-release/00-build-truth.md:349-361`. Bundles refuse `DEPLOYMENT`-class changes by design (`GateConfigBundle.java:258`): windows, schedulers and horizons ship in a build.
6. **Production is the 7 CPLM jobs on one 16-slot TaskManager, no HA, no supervisor**, air-gapped, on a disk shared with Instrumental (`prod_decision.md:10-19`); a TM restart returns every job to fresh window state (`checklist.md:201`). Kafka retention is at the minimum; IoTDB/Postgres are the records (`topics.txt` header).
7. **Watermarks**: assign at the source per partition, mark control streams idle, idleness 30 min; connecting a `noWatermarks()` stream after the assigner stalled the long job for an hour (`CplmIngestPipeline.java:142-146,:189-196`).
8. **Bounded sources feeding a KafkaSink** in a streaming job trigger FLINK-25920 on restore (`AnnounceOnceSource.java:464-472`); bounded REST submissions leak TM metaspace (`checklist.md:201`).
9. **Evidence volume**: episodes ≈ every window at plant scale; Short-tier artifacts are off at the source (`04b:92-101`; `prod_decision.md:42`).
10. **Alarm identity rule** `[^A-Za-z0-9_]→_` over `alarmId` is shared by three codebases and must not change alone (`IoTDBPersistenceJob.java:128-131`).
11. **Config that a worker cannot attribute is NACKed `UNSIGNED`**: the Flink containers need `CPLM_GATE_CONFIG_KEY` = `TRAVERSE_SERVICE_KEY` (`docker-compose.yml:526`, `marun.yml:256`).
12. **Unknown catalogue properties are rejected** (`GateConfigBundle.java:278,:290`); the catalogue hash is checked on PREPARE (:251-253) - the bundle plane is closed to new property kinds without a jar + catalogue release.

## 6. Open questions

1. Would a Truss runtime package travel on the existing bundle plane (signature, catalogue validation, PREPARE/APPLY, capability) or on a new topic with its own worker-side validator? The current validator rejects any property outside the 165-entry catalogue and any scope other than SITE/PROFILE/LOOP.
2. Who assigns `entity_id` and where is the alarm → entity mapping? Alarms are keyed by `serverId|source|condition` with no asset lookup in Flink; loops carry `asset_uuid` only when ingestion knows it. **(inferred)** an enrichment stage or a keyed join against a broadcast entity map would be new code in every job.
3. Production runs only the 7 CPLM jobs with no supervisor and no HA; a new runtime job needs a place in `04b-submit-flink-jobs.sh`, `.env` switches, and a resubmit/upgrade procedure that does not rely on savepoints (none are used today) - or a decision to start using them.
4. State evolution: keyed state is Java POJO via `TypeInformation`; today every breaking change is cancel + fresh submit and a TM restart loses window state. Is that acceptable for long-lived per-entity state, and which fields need a versioned serializer?
5. Sinks: keep the Flink → Kafka → consumer pattern (edge node for MQTT/Redis, .NET for Postgres) or add Flink connectors? `flink-connector-jdbc` is on the classpath but unused, and the "PostgreSQL is written only by projection consumers" rule would change.
6. Capacity: one 16-slot TaskManager (2560 m) already hosts 7 jobs with 24 h buffers per loop and a known metaspace leak; a per-entity runtime with window buffers for every asset needs sizing before the pitch's state model is committed to.
7. Should the unused `DB_URL`/JDBC dependency, the sink-less `KpiMap`, the consumer-less `live.alarm.metrics` sink and `CplmGateStreamJob` be removed before adding a new runtime, so the fleet's real surface is what the audit lists?
