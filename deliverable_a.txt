Deliverable A – Edge Application Specification
1. Purpose, Scope, Deployment Context
The Edge Application (collector) runs at each PDO site to interface the local DCS OPC A&E servers and
ingest alarm/event data into Kafka. It is responsible for subscribing to each OPC A&E server via local
COM/DCOM (no network DCOM or tunnellers) and streaming events northward. The collector may
be deployed co-resident on the OPC server host or on an adjacent VM on the same secured subnet (co-
located to satisfy the “local COM” requirement). Assumption: the PCD allows installing a Windows-based
agent in either configuration. Containerisation (Docker/Kubernetes) in PCD is an open item: if
disallowed, use Windows Service or similar . 
The collector’s scope is alarm ingestion and normalization only; operator acknowledgement and shelve
commands are sent back to the DCS via the collector . No UI or KPI functions are handled at the edge. It
must support 74 heterogeneous sites with multi-OEM DCSs (Honeywell, DeltaV, Yokogawa, Foxboro, ABB,
GE, etc.). All upstream transport is via Kafka over TLS (no remote DCOM). The target end-to-end latency
is “near-real-time” (~5–10 s). Any stricter requirement (≤5 s) is flagged as an open item, since worst-case
latencies (COM callbacks, Flink processing, network) may exceed it. 
Power/space constraints in PCD mean the collector should be lightweight: minimal CPU/RAM footprint
(e.g. <2 vCPU, <4 GB RAM per site) if co-resident. Adjacent-VM deployment allows slightly higher
resource budgets. The service must run under a least-privilege account and be hardened (firewalled
except Kafka endpoints, patched, etc.). Use TLS/mTLS for Kafka; OPC COM remains local-only. 
Open items: Data-diode vs. bidirectional firewall at PCD↔IOC (determines whether write-back ACKs can
flow down); exact hosting (co-resident vs. adjacent VM); PCD virtualization policy; AVEVA System
Platform integration. 
2. OEM Connector Abstraction
Define a plugin-based Driver Interface (e.g. a C++/C# class or service) with methods: connect(), 
subscribe(), refresh(), processEvent(), acknowledge(), and disconnect(). Concrete
drivers implement this interface per OEM (plus Foxboro’s SQL driver and an optional OPC UA A&C
driver). Each driver reads configuration (e.g. CLSID/ProgID, connection params, filter criteria, tagging
rules) and handles OEM-specific details. 
Honeywell Experion (Classic/TPS/TDC): Uses the Experion OPC A&E server . Native alarm
priorities: Journal, Low, High, Urgent. Map these into OPC severity (1–1000) and CAS priority

supply any Honeywell-specific area/asset attributes (e.g. Area Name, Alarm Class) found on the

swapping to UA (via UA Client library) if the site supports it.

Warning, Advisory (plus Diagnostics) by alarm definition. Map Critical→high severity,

includes: server identifier , filter criteria (areas, severity range, event types), and normalized area/
asset names. 
3. Connection & Subscription Management
Each driver creates one OPC A&E subscription ( IOPCEventServer::CreateEventSubscription)
per OPC server (the “single string” requirement). Upon connect (and on reconnect after any failure), the
driver must explicitly call Refresh()  to retrieve all currently active/unacknowledged conditions
(building the current alarm summary). The COM subscription should specify minimal filtering on the
server (e.g. limit to “Condition events” or configured areas/severity ranges) but rely mainly on edge
filtering for precise needs. Use IOPCEventSubscriptionMgt::SetFilter judiciously: server-side
filtering reduces load, but we must keep one subscription per server and handle all relevant events in
our code. 
The driver must implement robust session management: if the COM connection breaks or the OPC
server goes down, the driver should automatically retry with exponential backoff, log errors, and
resume subscriptions. On reconnect, call Refresh() again to reconcile any missed changes. Track
a simple heartbeat metric (e.g. last-event timestamp per server) and alert if no events arrive for a
configurable timeout.

5. Normalisation at the Edge
At ingestion time, the collector converts vendor-specific values into the CAS canonical scheme: 
Severity/Priority Mapping: For each OEM, define a table mapping native priority levels to OPC
1–1000 and to ISA-style priorities. For example, Honeywell’s Journal/Low/High/Urgent might map
to OPC severity 100/400/700/1000, and to ISA priority 4/3/2/1 respectively. DeltaV’s Advisory/
Warning/Critical map similarly (Advisory≈low, Critical≈high). Yokogawa’s numeric priority bands
map into 1–1000 linearly. Define these mappings in configuration. 
Area/Asset Normalisation: Extract vendor “area” or “unit” attributes (e.g. Experion Area, DeltaV
Area, Yokogawa Unit) and map them to a common area field. Similarly map any asset or unit
identifier to asset. If vendor provides hierarchical tags, flatten or concatenate (e.g. Area1/
Unit5). Missing fields default to empty.
Message Normalisation: The message text may include codes or parameter values; retain it
verbatim. Remove any binary non-text attributes.
Timestamps: As noted, use controller-provided time if available; otherwise use ingest time and
set timestampFidelity="ingest". Store both activeTimeMs (the stable SOE anchor) and 
eventTimeMs (callback receipt time) in the record for later ordering. 
Watermark Assignment (for Flink): The edge Flink job (Section B5) will use activeTimeMs as
event time with bounded out-of-orderness. At ingest, annotate each event with a “fidelity” flag to
let Flink decide if it can be used as watermark basis (if timestampFidelity="device") or if it
should be ignored or held (if low fidelity).
After normalization, the driver publishes the normalized event record to an edge Kafka topic (e.g. 
Site007.normalised-events), partitioned by siteId and perhaps hash(source). It also forwards

6. Store-and-Forward & Backfill
Each site has a local Kafka broker (or cluster). The raw-events topic (and normalised-events, alarm-
state, etc.) use Kafka’s retention to buffer data during upstream outages. For example, retention should
exceed the longest anticipated IOC unavailability (e.g. hours/days). This ensures zero alarm loss: when
the IOC link is down, Edge Flink continues processing locally. 
On reconnect, Kafka’s retained log is replayed. Use Flink’s event-time processing (with watermarks) so
that replayed (late) events still integrate correctly into the site’s state. The Flink job will have logic to
allow a bounded lateness (e.g. up to a few minutes) and side-output any excessively late events for
analysis. 
The collector ensures ordering by writing events to Kafka in the order received. The activeTimeMs
embedded in each event allows Flink to restore SOE order across sites when we replay. 
Sizing: The site’s Kafka broker must allocate disk for retention based on worst-case alarm flood rates
and retention period. For example, if a site can produce 1000 alarm events/sec (worst-case flood) and
we retain 24 h, that’s ~86.4M events; at ~1kB each, ~80 GB. This should be computed per site (open item:
actual expected flood rate, retention targets). 
7. Acknowledgement / Command Handling (Write-Back)
The collector subscribes to a local Kafka commands topic (e.g. Site007.cmd-ack) for operator
actions from IOC. Messages include: {siteId, source, conditionName, activeTimeMs, 
commandType, commandId, timestamp}. When a command is received: 
Ack Command: On receiving an ACK command, the collector looks up the corresponding OPC
Cookie by matching (source,conditionName,activeTime) against a cached or queried 
IOPCEventServer.GetConditionState call. (The cookie in events is session-bound, so it
must be resolved live.) Then call IOPCEventServer::AckCondition(source, 
conditionName, activeTime, cookie). Upon success, log and (optionally) publish an “ack-
command-sent” event locally. If the DCS is disconnected or not acknowledging, the command
should be retried or logged as error . Command idempotency is ensured by client-assigned
unique commandId (ignore duplicates). 
Shelve/Suppress Command: If shelving or disabling is supported, similar pattern: translate to
the DCS’s mechanism (e.g. DeltaV’s shelving APIs). These commands also originate from the IOC
and flow to the collector , then to the DCS via the appropriate API. The collector may not
implement shelf logic itself (Flink handles the conceptual state); it merely executes operator
shelve/cancel commands on the DCS. 
Command Flow Guarantee: Because of potential one-way connectivity, the UI should not
assume an ACK is completed until the DCS emits a new event with the ACKED bit. Therefore the
UI must wait for the OPC server’s ACK confirmation. The collector does not update UI state

8. Security
OPC Security: The edge service communicates to OPC servers only via local COM; no DCOM
opens ports, so no external OPC access. Disable network DCOM entirely. 
Kafka Security: Use TLS encryption and mTLS certificates on all Kafka brokers (Edge and IOC).
Use Kafka ACLs to restrict producers/consumers by service account. Each edge service should
have its own Kafka principal with write access only to its site’s topics and read access only to its
inbound commands. 
Service Accounts: The collector should run as a low-rights user on Windows, only with privileges
needed for COM/OPC and network Kafka. 
Hardening: Whitelist executables in AV/Endpoint Protection to allow the collector’s binaries and
Kafka clients. Ensure the Windows instance is patched. Restrict network firewall: allow only
required ports (OPC via localhost COM, Kafka TLS out to IOC cluster , no inbound from outside
except maybe Management).
9. Resource & Footprint
Estimate per-site collector footprint (co-resident): about 1–2 vCPUs and 2–4 GB RAM should suffice
under normal load. An adjacent VM can provision more if needed. Kafka broker on site: if single-node,
allocate at least 100 GB disk for retention (size = event rate × retention). RocksDB state from Flink
requires disk space (see section B9). The CPU load is bursty (on alarms); idle otherwise. Edge Flink job:
allocate parallelism ~1–2 and memory ~4–8 GB. 
If co-resident, resource budget must fit on DCS hardware (often few-core servers). If an adjacent VM is
used, resources can be dedicated. Monitor actual usage during testing and adjust. 
10. Configuration & Lifecycle
Centralize configuration in a version-controlled repository or config management system. Each site’s
config includes DCS server list, OPC ProgIDs, filter settings, normalisation rules. The collector can auto-
discover new OPC tags if needed via OPC DA browse, but major new alarms should be handled in DCS
configuration and then flow through automatically via Refresh(). Versioning: use a config schema
with semantic versioning. Upgrades: use Kafka and Flink savepoints; collector upgrades can be done
per-site in maintenance windows. 
Open item: How are new alarms discovered? We assume OPC servers always list all conditions, so the
collector just sees them on Refresh() or on event. No manual tag list needed.

11. Observability
Expose Prometheus-style metrics: per-OPC-server events/sec, COM connection status, Refresh latencies,
Kafka produce/consumer lag. Log to local file (rotate daily) and to a central log aggregator . Tracing:
instrument critical paths (subscription calls, ack calls). Alerts: fire if any OPC server is disconnected >X
minutes, or Kafka backlog exceeds threshold. Also emit count of events dropped or errors. 
Local dashboards (or IOC dashboards) should show each site’s connectivity (OK/NOT), event rate, and
per-server last event time. 
12. Failure Modes & Test Plan
OPC Server Down: Collector loses connection and retries. Edge Flink should detect lack of events
and mark alarms stale if no refresh occurs. On server restart, collector re-subscribes and issues 
Refresh(), Flink reconciles state (see B10). 
Network (PCD↔IOC) Down: Kafka local buffer fills up to retention limit; edge Flink continues
normal operation autonomously. When network recovers, data replicates to IOC. 
Edge Restart: On restart, collector re-subscribes and Refresh() gets current active alarms
(ensuring no missing clears); then it consumes from Kafka from last committed offset to catch
up. 
Partial OEM Outage: If one OEM’s OPC server hangs, collector continues other servers. Flink
state for that site still valid for other alarms. 
Backfill Test: Simulate IOC outage, then flood X alarms, then restore. Verify all alarms appear at
IOC in correct SOE order . 
FAT: Build a test harness simulating OPC A&E servers (or use DCS test mode). Generate alarms at
known times, including duplicates and chattering. Verify edge and IOC processing (state
machine, exactly-once, no duplicates). 
Security Test: Verify no COM over network, Kafka TLS enforced, service runs without admin
rights. 
Deliverable B – Flink Alarm-Lifecycle State-
Management Specification
1. Two-tier Responsibility Split
Edge Flink (Per-Site): Processes raw/normalized events for that site only. Responsibilities: apply OEM-
specific mappings (completed by collector), assign event-time/watermarks per source, deduplicate
(drop repeated identical notifications based on changeMask), detect local chatter/flood and mark
affected alarms, and maintain a site-local alarm state machine (first-line lifecycle). It emits “site alarm
state changes” (activations, clears, acked transitions) and computes local KPIs (e.g. site alarm rate) for
local dashboards. While the IOC is disconnected, edge Flink state is authoritative for that site. 
IOC Flink (Enterprise Level): Aggregates all sites. It ingests replicated normalized events and
(optionally) site-state events. Its responsibilities: maintain the authoritative consolidated alarm state
across sites, correlate alarms (e.g. same physical asset alarms), compute ISA-18.2/EEMUA metrics
(operator workload, flood %, standing alarms, etc.), and serve state for the UI. IOC Flink also
orchestrates command routing: it takes UI commands, forwards them to the correct site’s command

State Authority: During normal operation, IOC Flink is source-of-truth for the global view, but edge

state by re-injecting any missed events (via Kafka backfill) – see B10. 
2. Job Topology
Each tier may run one Flink job, or a few dedicated jobs. For simplicity, use one job per tier with logical
subgraphs. Edge Flink job: Source = Kafka consumer on site.raw-events; then 
keyBy(alarmInstanceKey) into a ProcessFunction implementing the lifecycle state machine.
Side-output chatter/flood alerts. Sink: Kafka to site.state-changes, and optionally 
site.current-state. IOC Flink job: Source = Kafka on all sites’ normalised-events (or on replicated 
state-changes), keyBy (siteId,source,conditionName); state machine in a
KeyedProcessFunction merges cross-site logic; compute cross-site metrics; sinks: 1) to log-compacted
current-state topic, 2) to history store, 3) to dashboards. Commands: a separate Kafka source for 
commands stream, keyed by (siteId,source,conditionName), routed to state processor . 
A unified job is feasible, but separating edge vs IOC allows scaling and loose coupling; however , each
can run identical code with different parameters. 
3. Keying
The alarm instance key is (siteId, source, conditionName). This uniquely identifies an alarm
definition in the plant. Using this key groups all events of one alarm to the same partition and state.
SiteId distinguishes site scope. The key cardinality is number of unique alarms per site (O(10⁴–10⁵)).
Kafka topics partition by site (and key) for parallelism. Flink parallelism should match Kafka partitions to
avoid skew. Use consistent hashing on this key for partition. 
4. State Primitives
Use Flink keyed state: 
ValueState<AlarmState>: The current state of the alarm instance, containing fields:

the active cycle and any pending ack command ID. 
ListState<EventRecord>: (Optional) history of recent events for this alarm (e.g. last N
subcondition changes) to support chatter detection or windowed metrics. 
MapState<String, Long> chatterWindow: For counting flaps, store timestamps of recent
transitions. 
AggregatingState or ValueState<Long> for counters/metrics (e.g. count of transitions in
window).

5. Event-Time & Watermarks
Assign event-time from the alarm’s activeTimeMs (which is the controller SOE). Use 
WatermarkStrategy.forBoundedOutOfOrderness(Duration.ofSeconds(X)) where X is chosen
based on network jitter (e.g. 10s). Mark an event-time idleness per key after no events for some time to
avoid stagnation. For low-fidelity sources (Foxboro), use ingestion time but emit a watermark that lags
(i.e. treat watermark = current processing time minus a large bound). Propagate a 
timestampFidelity flag through Flink so sinks know which events have real-time stamps vs not.

7. Timers
Event-time timers: Implement off-delay or debounce if needed (e.g. if hardware reports
flapping on spike, wait a few ms before final state). Also may use event-time timers to emit KPI
intervals (though IOC does that). 
Processing-time timers: For auto-unshelve (expire shelve after a timeout) and to clear stale
state. For example, if an alarm remains active but no event seen for a long time, one might clear
it (depending on design). 
For standing alarm cleanup: if an alarm stays active but stale (no corresponding process data), a
timer could re-query or clear . 
Timers can also schedule window rolls for chatter detection: e.g. after 1-minute window, collapse
chatter count. 
8. CEP / Flood & Bad-Actor Logic
Chatter Detection: Maintain a sliding count of how many times this alarm state flipped
(Active→Inactive→Active, etc.) within a short time window. Use Flink’s CEP or just keyed state
with timers. If count > N in T seconds (configurable, e.g. 3 flips in 10s), emit a “chatter” event on a
side-output for that alarm, and optionally suppress emitting repeated notifications (e.g. throttle
further active events for a short quarantine). 
Flood Detection: Count total alarms (across conditions) per site/area in sliding window. If alarm
rate > threshold (EEMUA suggests e.g. >10/min/operator), flag an “alarm flood” to raise an alert
or trigger load-shedding. 
Bad-actor Ranking: Maintain per-alarm counters (all-time or sliding) of activations. Periodically
output metrics (e.g. top 10 alarms by count) to help rationalization. 
These analyses can be side outputs to monitoring topics or a metrics store.

Enable Kafka checkpointing: the KafkaConsumer should commit offsets on checkpoint. Use a Kafka

10. Recovery & Refresh() Reconciliation
On restart, Flink restores from the last checkpoint (state is recovered). Immediately after startup, the
collector drivers will issue OPC Refresh() calls, generating a burst of “refreshed” events. These
must be processed by Flink to reconcile any changes that occurred during downtime. For example, if an
alarm was acked while Flink was down, the refresh event will show it active+acked or inactive. The
transition function should compare restored state vs incoming refresh state: any difference should be
emitted as a state-change event. For example, if Flink thought an alarm was ActiveUnacked but refresh
comes in as Inactive (implying Clear+ACK happened), then Flink should move to Normal and emit
Clear+Ack events. Treat refresh events like normal events, but note they may come out-of-order . 
Rule: If refresh timestamp < current state lastChangeTime, ignore as stale. Otherwise, apply transitions
normally. 
11. Backfill Ordering
Because Kafka partitioning by (site,key) and Flink event-time, backfilled events will be ordered into
proper SOE order by the watermark strategy. Set a maximum lateness (e.g. 1 min) so late events are still
processed; any events beyond lateness go to a “late” side output topic rather than be dropped. The
result is a correct millisecond-resolution SOE ordering, satisfying the fidelity requirement. 
12. Serving the Current State
Maintain a log-compacted Kafka topic (e.g. alarm-current-state) keyed by 
(siteId,source,conditionName). Upon each state change (active, ack, clear), output a message
with the new full alarm state (active/inactive, acked/unacked, severity, priority, lastChangeTime, etc.)
under that key. Because it is compacted, the topic always retains the latest state per alarm. A
WebSocket/SSE gateway can tail this topic to push updates to HTML5 clients. Do not rely on Flink
Queryable State for UI (it is optional) – instead use Kafka. Also sink a full history of alarm-state-change
records to a time-series database or historian (e.g. InfluxDB, OSI PI) for audit.

13. Command / Ack Orchestration
In IOC Flink, subscribe to the consolidated commands topic (all UI-generated ack/shelve commands).
Key by (siteId,source,conditionName) and correlate against current state. For an ACK
command, mark the alarm state as Ack-Pending (perhaps set a flag in state). Produce the command onto
the edge’s Kafka command topic (routed by siteId). Only when the corresponding condition event with 
ACKED=true flows back up from the edge (via normal event flow) do we mark the pending as
completed and update the state to acked. This ensures the UI only sees the ACK when the DCS has
confirmed it. Use the command’s unique ID for idempotency (ignore duplicate commands). All
commands (and their outcomes) should be logged for audit. 
For shelving commands, simply update the state and pass the command down, then clear state when
the shelve expiry event returns. 
14. KPIs & Analytics
Calculate ISA-18.2/EEMUA KPIs in IOC Flink (or export to a monitoring system): 
Alarm Rate: count alarms/operator/min. (From ISA: aim <1–2 alarms/10 min; alert if above). 
Standing Alarms: count of alarms active > X hours (per EEMUA guidance). 
Flood Percentage: fraction of alarms during flood conditions. 
Nuisance/Repeater Alarms: list alarms that exhibit chattering or high recurrence. 
Operator Response: distribution of Ack times (time from event to ACK). 
Emit these metrics periodically (via Prometheus, Grafana, or push to an analytics DB). Also maintain SLA
alerts (e.g. if avg ack time > Y, etc.).

16. Scaling, HA & Sizing
Parallelism: Flink parallelism must match Kafka partitions (e.g. 4–8). Key cardinality per partition
(~100k alarms) is manageable with RocksDB. 
Checkpointing: Store to high-availability storage (e.g. HDFS/MinIO) with replication. 
Throughput: Input sizing = peak alarm rate across all sites (e.g. assume 1000 events/sec/site *
74 sites = 74k events/s). Ensure cluster can handle bursts. 
State Size: Estimate state entries = total configured alarms (maybe 100k/site active config, 74
sites → 7.4M keys worst-case) but active subset is smaller . Use a cluster of several Flink
TaskManagers (e.g. 10–20 nodes) for headroom. 
Topic Partitions: IOC topics partitioned by site then by alarm key, to spread load. 
HA: Run Flink in cluster mode (YARN/K8s), with standby JobManagers. Kafka cluster should be
multi-broker with replication across zones. 
17. Test & Verification
Unit Tests: For the state machine logic (all transitions), including edge cases (e.g. double-acks,
disable/enable during active). 
Integration Tests: Simulate OPC event streams (including out-of-order and duplicate events)
and verify final state. 
Outage Tests: Simulate IOC or Edge failures; verify that on recovery, the combination of Kafka
retention and Refresh() leads to correct state. 
Exactly-Once Test: Kill Flink tasks mid-processing; after recovery, ensure no lost or duplicated
events (via comparing counts). 
Chatter/Flood Tests: Inject rapid flapping alarms and bursts to confirm detection logic triggers. 
Performance Test: Load-test with synthetic alarm floods at or above expected peak to size the
Kafka retention and Flink cluster . 
End-to-End Test: From DCS to UI: generate alarms on DCS, observe them on web banner ,
perform ack, and confirm UI updates only after DCS echo.
